# agent-projects — Specification

**Status:** Draft
**Size:** Large (multi-component; one change lands in a third-party repository)
**Repos touched:**

| Repo | Role |
| --- | --- |
| `sipeed/picoclaw` (upstream) | Glob support in `agents.dispatch` selectors — the enabling change |
| `crab-shell-proxy` | Project store, config projection, workspace seeding, project-scoped endpoints |
| `crab-exoskeleton-webapp` | Project UI — **out of scope here**, contract only (§ Interface for the webapp) |
| `zombie-crab-project` (parent) | Gateway route declarations for the new `/v1/projects` surface |

---

## Problem

A user has one agent and one workspace per `(agent, user)`. Every conversation
shares the same files, the same `AGENT.md`, and the same accumulated memory.
There is no way to say "this thread is about the seed-trial analysis, keep its
files and its instructions apart from my other work" — the thing Claude Projects
and ChatGPT Projects both provide.

picoclaw already has the machinery: `agents.list` gives an agent its own
workspace, model and skill set, and `agents.dispatch` routes a message to it.
What is missing is a way for a **user** to create that configuration from the
frontend, and a routing scheme that survives many conversations per project.

## Goal

A user creates a project from the webapp. From then on, chats opened inside that
project run as a distinct picoclaw agent with its own workspace and its own
instructions, while inheriting everything from the parent agent — skills, model,
credentials, and every `agents.defaults` setting including `image_model`.

## Non-goals

- **Any frontend.** `PROJECT.md` is explicit that this service is API-only. This
  spec defines the contract the webapp consumes.
- **Sharing a project between users.** A project belongs to one
  `(tenant, subscription, agent, user)` tuple, like the workspace it lives in.
- **Cross-project delegation.** `subagents.allow_agents` stays unset; project
  agents cannot spawn each other (see NFR-4).
- **Shared-files cascade inside project workspaces** (DEC-3). Tenant and
  subscription shared files remain available in the main workspace only.
- **Per-project model or skill *overrides*.** v1 inherits; choosing a different
  model per project is a later feature (see § Deferred).

## Requirements

### Upstream: dispatch selector globs

**FR-1** — `agents.dispatch.rules[*].when.<selector>` MUST accept `*` as a
wildcard matching any sequence of characters, including the empty sequence, in
all six string selectors (`channel`, `account`, `space`, `chat`, `topic`,
`sender`).

**FR-2** — A selector value containing no `*` MUST be compared exactly as it is
today. Existing configurations MUST behave identically. (Verified by keeping the
current `route_test.go` cases green and unmodified.)

**FR-3** — No metacharacter other than `*` is recognised. `?`, `[`, `]` and `\`
are literal characters. There is consequently no such thing as an invalid
pattern, and no error path where a malformed rule could become a catch-all
(DEC-5).

**FR-4** — The change ships as a **build-time patch overlay**: a Dockerfile that
clones `sipeed/picoclaw` at a pinned tag, applies a `.patch`, and builds the
image `picoclawImage` points at (DEC-2). Nothing in this feature waits on
upstream.

**FR-4a** — The patch is written to be upstreamable from day one — tests
alongside `pkg/routing/route_test.go`, a `docs/guides/routing-guide.md` update,
and no zombie-crab-specific content — so that opening the PR later is
transcription, not rework. Whether to open it is decided after the patch is
proven in production. See design.md § Upstream contribution.

### Proxy: the project record

**FR-5** — A project is `{id, name, instructions, createdAt}` persisted in
`.projects.json` in the user data dir, adjacent to `config.json` and therefore
above `workspace/` — unreachable by the agent under `restrict_to_workspace`.

**FR-5a** — `id` is generated by the proxy from `name`, normalized to
`[a-z0-9][a-z0-9_-]{0,63}` so it survives `NormalizeAgentID` unchanged (VER-11),
and made unique within the user's project set. A user-supplied ID is never
accepted: it feeds an agent ID, a filesystem path and a dispatch pattern.

**FR-5b** — `id` MUST NOT be `main`, and MUST NOT collide with an existing
project's ID.

### Proxy: config projection

**FR-6** — On every ensure, `agents.list` is rebuilt from the project store as:
one explicit default entry `{id: "main", default: true}`, followed by one entry
per project `{id, name, workspace: "<home>/.picoclaw/workspace-<id>"}`. Whenever
the list is emitted at all it MUST carry the explicit default entry, because a
non-empty list removes picoclaw's implicit `main` (VER-8).

**FR-6a** — With **zero** projects the projection emits neither `list` nor
`dispatch`, and removes them if a previous projection left them behind.

Amended during implementation. The original wording said the default entry was
written *unconditionally, including when there are no projects*. That is
over-strict and actively harmful: it would add an `agents.list` key to the
`config.json` of **every existing user** on their next chat — a fleet-wide config
rewrite, and a drift signal, to express something picoclaw already does for free.
VER-8's hazard only exists once the list is non-empty. Omitting the key entirely
is what makes NFR-5 literally rather than approximately true.

**FR-7** — Project entries MUST NOT carry `model` or `skills`. Inheritance is by
omission (VER-1, VER-2). A projection that writes either is a defect: it would
pin a project to a model the registry no longer resolves, or freeze its skill set
against the admin shared-skills cascade.

**FR-7a** — `agents.dispatch.rules` is rebuilt as one rule per project:

```json
{ "name": "proj-<id>", "agent": "<id>",
  "when": { "channel": "pico", "chat": "direct:pico:p.<id>.*" } }
```

No catch-all rule is emitted. A message matching nothing falls through to the
default agent, which makes rule ordering irrelevant.

**FR-7b** — The projection MUST occur inside the same read-modify-write that
materializes the model (`materializeModels`), not as a separate write. A separate
write is erased on the next ensure (DEC-6).

**FR-7c** — `agents.defaults` MUST NOT be touched by the projection. It is owned
by model materialization.

**FR-7d** — `agents` remains a managed config path: `IsManagedConfigPath`
continues to reject admin edits under it. Projects are written by this new
proxy-owned path only; the guard is not relaxed.

### Proxy: session routing

**FR-8** — For a chat that names a project, the session ID sent to picoclaw is
`"p." + projectID + "." + SessionKey(accID, clientSessionID)`. For a chat with no
project it is unchanged, and can never match a project pattern.

**FR-8a** — The proxy MUST reject a request naming a project that is not in the
store, rather than falling through to the default agent. Silent fallback would
write the user's conversation into the wrong workspace.

### Proxy: workspace seeding

**FR-9** — On project creation the proxy creates `workspace-<id>/` with
`sessions/`, `memory/` and `uploads/`, and chowns the tree to `picoclawUser`.
picoclaw would create the bare directory itself (VER-7), but as root-owned and
empty.

**FR-9a** — `AGENT.md` is written by the proxy: the resolved parent `AGENT.md`'s
frontmatter preserved verbatim, with the project's instructions appended to the
body. Preserving frontmatter is what carries the parent's declared tools and
skills into the child.

**FR-9b** — `SOUL.md` and `HEARTBEAT.md` are copied from the resolved persona
cascade into the project workspace on **every** ensure, so an admin persona
change reaches project workspaces the same way it reaches the main one. They are
copies, not binds (DEC-3); overwriting them reproduces the effect the main
workspace gets from a read-only mount.

**FR-9e** — `USER.md` is seeded **only when absent**, never refreshed.

Corrected during implementation: it was originally in the refreshed set, which
erased the project agent's accumulated knowledge of the user on every message.
`USER.md` is the one identity file the main workspace deliberately leaves
writable — it is excluded from `PersonaMounted` precisely because the agent
accumulates what it learns there, and `provision.go` seeds it once so "a
returning user's evolved files are never clobbered". A project agent builds its
own picture of the user, in its own workspace, and needs the same treatment.

**FR-9c** — The effective secrets directory is bind-mounted read-only at
`workspace-<id>/.secrets`, mirroring the main workspace's mount.

**FR-9d** — No skills work is required: the effective-skills directory is already
mounted at the global `~/.picoclaw/skills`, outside every workspace (VER-2).

### Proxy: lifecycle

**FR-10** — Creating or deleting a project recreates the user's container, because
it adds or removes a bind mount. This is accepted: it is a deliberate, infrequent
user action, and the codebase already recreates on persona drift.

**FR-10a** — Renaming a project or editing its instructions MUST NOT recreate the
container. Instructions are a file write inside an existing mount; a rename
touches only `name`, which is descriptive.

**FR-10b** — Deleting a project deletes its workspace, including its transcripts.
The API MUST make this explicit; the webapp is expected to confirm.

### Proxy: project-scoped endpoints

**FR-11** — `GET|POST /{agent}/v1/projects`, `PATCH|DELETE /{agent}/v1/projects/{id}`.
REST, consistent with the rest of the proxy's own HTTP API — the JSON-RPC rule in
the root `CLAUDE.md` governs calls *to mycelium*, not this surface.

**FR-12** — `/v1/chat/completions`, `/v1/sessions/history`, `/v1/media` and
`/v1/cron/tasks` accept an optional `project`. Absent means the main workspace and
today's behavior, unchanged.

**FR-12a** — The path helpers that hardcode the `workspace` segment —
`SessionsDir`, `CronFile`, `UploadsDir` (`internal/config/config.go:501,510,518`)
and the memory dir (`internal/docker/memory.go:24`) — take the segment as a
parameter. Every caller passes `"workspace"` unless a project is named.

**FR-13** — Permissions match the surrounding surface: reading projects requires
`read` on the agent; creating, editing and deleting require `write`.

## Non-functional

**NFR-1** — The config changes exactly once per project lifecycle event, never
per conversation. This is the property the whole design exists to obtain.

**NFR-2** — No `/reload` call is on the critical path. Project creation recreates
the container, which picks up the config anyway (VER-9).

**NFR-3** — A project ID can never inject a metacharacter into its own dispatch
pattern: FR-5a's alphabet excludes `*`, and `.` is excluded by construction
(VER-11).

**NFR-4** — The main agent gains picoclaw's `delegate` tool as soon as one
project exists — registration is gated on agent count alone (VER-10). It is
inert because authorization is separately gated and fails closed with
`subagents` unset. Declared here so it is not diagnosed later as a regression.

**NFR-4a** — The projection MUST NOT emit `subagents.allow_agents` on any entry,
and MUST never emit the literal `"*"`, which picoclaw reads as "allow every
agent" (VER-10). That would let the main agent delegate into any project's agent
and therefore into its workspace, defeating the isolation the project boundary
exists to create.

**NFR-5** — A user with no projects sees byte-identical behavior to today:
`agents.list` gains one explicit `main` entry, which
`NewAgentRegistry`/`resolveDefaultAgentID` treat exactly as the implicit one.

## Acceptance criteria

**AC-1** — With the patched picoclaw, a rule whose `chat` is
`direct:pico:p.demo.*` routes two different session IDs sharing that prefix to
the same agent, and a session ID without the prefix to the default agent.

**AC-2** — Existing `route_test.go` passes unmodified (FR-2).

**AC-3** — A project created through the API produces, in `config.json`, a
default `main` entry plus a project entry carrying **no** `model` and **no**
`skills` key.

**AC-4** — After **any** ensure, the `agents.list` and `agents.dispatch` in
`config.json` equal the pure projection of `.projects.json` — not merely "the
rule is still there". Asserting equality is what discriminates: a stale rule for
a deleted project, a list merged instead of rebuilt, and a rule written outside
the read-modify-write all fail the same assertion, whereas a survival check
passes for all three. This is the regression test for DEC-6.

**AC-5** — A chat sent with `project=<id>` writes its transcript under
`workspace-<id>/sessions/`, and `GET /v1/sessions/history?project=<id>` returns
it while the unscoped call does not.

**AC-6** — A project workspace contains an `AGENT.md` whose frontmatter matches
the parent's and whose body contains the project instructions.

**AC-7** — A skill added at tenant scope becomes visible to a project agent with
no config change and no project-side action (VER-2).

**AC-8** — A request naming an unknown project returns 404, and no conversation
is created (FR-8a).

**AC-9** — Deleting a project removes its list entry, its dispatch rule and its
workspace, and leaves other projects working.

## Interface for the webapp

The webapp consumes, and this spec does not design:

- Project list, create, rename, edit-instructions, delete.
- A project selector on the chat screen; the chosen project is sent as `project`
  on chat, history, media and cron calls.
- A visible warning on delete that transcripts and files are removed (FR-10b).
- A visible indication that creating or deleting a project restarts the agent
  (FR-10), consistent with how `restart-control` already surfaces bounces.

---

## Deferred

- Per-project model override (the registry cascade already has the levels; a
  project would become a fifth).
- Per-project skill subset — picoclaw supports it via `skills` on the list entry,
  but FR-7 deliberately does not use it in v1.
- Shared-files cascade inside project workspaces (DEC-3).
- Cross-project delegation via `subagents.allow_agents`.
- Using `POST /reload` instead of a container recreate for changes that do not
  touch mounts (VER-9).
